## 发布顺序

1. **先发布两个云函数。** 上传 `api`、`remind` 及各自 `package-lock.json`，安装锁定依赖。保持 API 手机号和订阅消息权限、现有网页后台登录规则。`remind` 配置至少 60 秒超时，代码在 45 秒后停止领取新任务；重新确认每五分钟触发器已启用。详情和个人历史是新增接口，必须先于客户端发布。
2. **检查数据库权限和索引。** 新增 `subscription_batches` 集合记录已处理授权批次，可提前创建；权限设为客户端不可读写。其余业务集合继续仅经云函数访问。确认活动 `status + date`、个人报名和提醒 `openid + createdAt`、积分流水 `openid + createdAt`、提醒 `eventId + sent`、订阅任务 `job + sent` 等实际查询所需索引。索引和生产权限本次未在线修改。
3. **上传电脑后台静态网页，再发布小程序。** 网页继续使用原有登录码、凭证和服务端管理员检查。两端需要一起更新，才能获得编辑版本和跨请求积分防重保护。旧客户端仍兼容，但没有操作 ID 的旧积分请求只能保证单次请求内一致性。
4. **真机验收。** 验证手机号同意与拒绝、登录返回、积分确认、报名与取消退款、订阅授权及实际送达；检查 iOS／安卓的小屏、大字体、弱网、安全区和返回行为。使用专用测试会员与测试活动，避免影响真实参与者。
5. **发布后观察。** 关注积分失败、报名错误、提醒 `failed` 和长期 `sending`、待发任务积压。发送结果未知的消息不能直接重置为未发送；先核查记录和微信结果，避免重复消耗授权。告警阈值由运营按实际流量设置。

旧补给计划保留兼容路径；新计划保存完整快照。会员赠分迁移会在会员进入时补齐标记与漏记流水，已领过的积分不会再赠送。提醒兼容没有批次字段的旧记录。

## 回滚

回滚前保存当前发布版本与配置，优先回滚出现问题的客户端或网页；服务端保留与新客户端兼容的接口和已落库数据。积分已提交的操作按流水核对，通过新的独立调整纠正，不能通过删除流水或直接改余额回滚。已经发送的订阅消息不回滚，也不清空批次记录重新发送。
